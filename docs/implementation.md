# 订阅系统实施记录

## 范围与设计

依据用户提供的 Daily Brief Radar v1.0 技术规格，先完成第一阶段数据模型、支付宝方案 A 订单匹配、内容快照及 Resend 发送，再制作网页入口。用户已授权按规格持续实施，在当前会话内直接执行。

沿用 Python，在现有仓库的新分支开发。SQLite 适合早期规模，所有服务必须共用持久文件。订单核验和有效期变更在同一写事务内完成。业务时间保存为 UTC。首轮实现采用罗马日期，后续按用户要求切换为北京时间，最新规则见下文调整记录。

采用数据库 outbox 作为初期队列，发送载荷与幂等键持久保存。Resend 幂等键有效期 24 小时，首次尝试超过 23 小时的未确认任务转人工核实，避免跨窗口重发。发送记录中的 success 表示服务商接受请求，最终邮箱送达需要服务商事件确认。

每日快照保存板块内容并禁止覆盖。订阅版生成器采用通用画像，复用已有采集、摘要及来源，个人版入口继续可用。支付通知需校验签名、应用、收款方、金额、交易状态和唯一流水。

## 2026 年 11 月 16 日：个人主页、登录链接与逻辑检查

### 检查结论

按代码和测试梳理完整链路：网页申请、邮箱确认、早晚报冻结、入队、worker 发送、退订、支付核验与续期。基线 55 项测试通过。真实 AI、Resend、支付宝尚未联调，仍以本地替身验证。

发现并处理的缺口：

1. 没有个人主页。管理页只能通过邮件里的链接进入，令牌存在 sessionStorage，关闭标签页即丢失，无法凭邮箱重新登录。
2. 看不到内容。管理页只显示偏好，没有简报内容。
3. 选中的主题在邮件里不突出。原先只有前三条展开，用户选择第 4 个及之后的主题会和未选主题一起被折叠。
4. 周付用户付款后立即收到“还有七天到期”提醒。
5. 登录、确认类事务邮件在发送队列中排在批量简报之后，早晚报高峰时会延迟。

### 实施内容

- 新增 `POST /api/login`。输入邮箱后，仅向已确认且状态为 active 或 expired 的账户发送登录链接。无论邮箱是否存在，响应一致。每个邮箱每小时三次，每个 IP 每小时二十次。登录邮件一小时内有效，退订后不再发送。
- 数据库升级到 v3，`delivery_log.task_type` 增加 `login_link`。SQLite 不能修改 CHECK 约束，因此在同一事务内重建发送表，保留全部历史记录并重建索引。v1、v2 均可升级，全新库直接使用 v3。
- 新增 `GET /api/feed`。需登录。仍在试读、付费或宽限期内的读者可看近 14 期（约一周）。试读用完或到期超过宽限期的读者只看最新一期并提示续费。未确认邮箱返回 403。`scope=followed` 只显示所关注主题，`scope=all` 显示全部并把所关注主题排在前面。未选择主题时返回通用版。
- 新增 `/login` 与重做 `/manage`。个人主页包含订阅状态与下一封发送时间、我的内容（关注／全部切换）、推送板块编辑、续费、退订、退出登录。保存板块后内容立即刷新。登录令牌保存到 localStorage，退出登录或令牌失效时清除。内容全部通过 textContent 渲染，链接只接受 http／https。
- 邮件按所选主题排列：所选主题全部展开，其余放入“其他值得一扫”。没有选择，或所选主题本期都没有内容时，保持通用版三条必知。仍遵守“偏好只影响排序，所有可用主题都保留”。
- 发送队列优先处理非简报类邮件，再处理批量简报。
- 周付订阅不再发送七天提醒，保留三天和一天提醒。
